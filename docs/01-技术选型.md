## 2. 后端语言评估：Go vs Java

> 评估基线：**仅基于需求与功能**，不引入团队/组织因素。

### 2.1 需求技术画像

- **业务域集中、规模中小**：商品展示、收藏、订单、会员，单库单域，无跨域复杂编排；
- **IO 密集型**：列表/详情查询、微信 HTTP 调用（登录、下单、回调验签）、媒体走 CDN（后端只做签名与元数据），全程无重计算；
- **外部依赖全部有标准方案**：微信小程序登录与 H5 OAuth（各一个 HTTP 接口）、微信支付 V3（双方均有官方 SDK）、JWT（标准方案）、PostgreSQL（两者的一等公民数据库）；
- **无高并发抢购场景**：活体宠物单只在售，防超卖用行级原子更新（`UPDATE ... WHERE status=1`）即可，不需要秒杀级架构。

### 2.2 逐项对照

| 需求项 | Go | Java | 判定 |
| ------ | -- | ---- | ---- |
| 账号体系 / JWT 双端隔离 | go-zero 内置 JWT 中间件，双 secret 易实现 | Spring Security 功能更深，但本需求是标准 JWT，用不到其深度 | 平手（均过剩） |
| 微信登录（小程序 code2session / H5 OAuth） | 一个 HTTP 调用 | 一个 HTTP 调用 | 平手 |
| 微信支付 V3（下单/回调验签/退款/对账查单） | 官方 `wechatpay-go`，功能完整 | 官方 `wechatpay-java`，功能完整 | 平手 |
| 订单状态机 / 超时关单 | DB 状态位 + 定时扫描，实现简单 | 同样简单 | 平手 |
| 商品 / 收藏 / 分类品种 CRUD | GORM + pgx 完整覆盖 | JPA / MyBatis-Plus 完整覆盖 | 平手 |
| 订单导出 Excel | excelize 足够优秀 | EasyExcel 更成熟 | Java 略优 |
| 宠物视频 / 图片 | 后端只管 COS 签名与元数据，播放由前端 + CDN 承担 | 同 | 平手 |
| 性能与资源占用 | 协程 + 低内存，同规格机器承载更高并发 | JVM 内存基线高，小规格机型开销占比大 | **Go 优** |
| 部署复杂度 | 单二进制（~20MB），Compose 单机即可 | JVM + fat jar，镜像大、需调优 | **Go 优** |
| 未来向复杂平台演进（营销中台/优惠券/多商户/复杂售后工单/大规模对账） | 生态可用但需自建较多轮子 | Spring 生态纵深大，成熟组件多 | **Java 优（仅当此类需求出现）** |

### 2.3 结论：当前需求下选 Go

1. **功能能力上两者完全等价覆盖本需求**——没有任何一项需求是 Java 能做而 Go 做不了的，反之亦然；所有「平手」项的差异只体现在代码风格，不影响交付；
2. 差异集中在**非功能维度**：本需求「IO 密集 + 中小规模 + 单机起步」的特征，让 Go 的资源效率与部署简单性**持续兑现**；而 Java 的生态纵深优势在本需求范围内**没有兑现场景**；
3. **翻转条件**（供评审确认产品路线图）：若明确规划演进为复杂电商平台——营销/优惠券体系、多商户入驻、复杂售后工单流、大规模财务对账——Java 生态优势开始兑现，届时应重新评估。仅就本文档锁定的需求范围，不存在该前提。

## 3. 前端跨端框架评估：Taro vs uni-app

需求 T1：小程序/H5 同一套代码仓库；未来可能支持 App。

| 维度 | Taro 4（React） | uni-app（Vue3） |
| ---- | --------------- | --------------- |
| 技术栈匹配 | **与团队现有 React 技术栈完全一致**（zustand、@tanstack/react-query 可直接复用） | Vue3，团队需新学 |
| 多端覆盖 | 微信小程序、H5、React Native（App）、鸿蒙 | 微信小程序、H5、App（uni-app x）、各家小程序 |
| H5 路由/SEO | 支持 BrowserRouter，H5 体验良好 | H5 成熟 |
| 小程序端稳定性 | 京东系大规模验证（京东 App 内众多小程序） | 国内使用量最大 |
| UI 生态 | NutUI-React（京东）、Taroify、antd-mobile 部分组件 | Vant、uni-ui，插件市场更丰富 |
| App 支持 | React Native（可）但实践成本较高 | App 支持更成熟 |
| 工程化 | Vite 构建、TS 友好 | Vite 构建、TS 友好 |

**结论：Taro 4 + React。**

理由：
1. 「一套仓库多端编译」两者均满足，决定性因素是**团队 React 资产与经验**——现有 awarelife-monorepo 全部为 React 19 + hooks；
2. 状态管理（zustand）、请求层（@tanstack/react-query 或自封装 Taro.request）、工具库可与 packages/ 共享；
3. App 端属于「后续可能」，届时再评估（Taro→RN 或独立 Flutter），不作为当前决策依据。

### 3.1 前端选型清单

| 类别 | 选型 | 说明 |
| ---- | ---- | ---- |
| 跨端框架 | Taro 4.x + React 18 | 编译目标：weapp（微信小程序）+ H5 |
| 移动端 UI | **NutUI-React 4**（京东出品，原生支持 Taro） | 电商组件齐全（商品卡、SKU、地址、瀑布流） |
| 备选/补充 | Taroify（Vant 的 Taro-React 版） | 补充缺失组件 |
| 样式方案 | Tailwind CSS + `weapp-tailwindcss` | 设计 Token 统一，小程序端类名处理 |
| 状态管理 | zustand | 与现有 monorepo 一致 |
| 服务端状态 | @tanstack/react-query v5 | 缓存、轮询支付结果 |
| 平台管理端 | React 19 + Vite 6 + Ant Design 5 + ProComponents | 与现有 manager 应用同构，共享包沉淀在 `packages/`（@pet/*） |
| 图表（平台端） | @ant-design/charts | 经营数据看板 |
| 表单 | react-hook-form + zod | 与现有 manager 一致 |
| 富文本编辑（商品详情） | md-editor-rt 或 wangEditor | 平台端编辑宠物图文详情 |

## 4. UI 设计方向（对应需求 R5）

### 4.1 移动端（用户端）

**风格定位**：温暖、活泼、高信任感 —— 活体宠物交易的核心是「让用户爱上这只宠物」，详情页以**大图 + 视频**为主体。

**参考的开源 UI / 设计体系**（均可在 npm/GitHub 查阅最新版本）：

| 项目 | 用途 |
| ---- | ---- |
| NutUI-React（京东） | 主组件库：商品卡片、瀑布流、地址、弹层、图片预览 |
| Taroify | Vant 风格补充组件：轻量、动效细腻 |
| Ant Design Mobile | 交互规范参考（表单、动作面板） |
| TDesign Mobile（腾讯） | 设计 Token 规范参考（色彩/圆角/字阶） |
| shadcn/ui | 设计趋势参考：留白、卡片化、细腻描边与阴影 |

**设计要点**：
- 主色：暖珊瑚/活力橙系（宠物亲和力），中性色高对比；
- 详情页沉浸式：视频/头图满屏、圆角卡片上浮、底部安全区操作栏（收藏 / 客服 / 立即购买）；
- 骨架屏 + 图片懒加载 + 视频封面 poster，弱网体验优化。

### 4.2 平台端（PC 管理端）

**结论：Ant Design 5 + ProComponents**（与现有 manager 应用同构，零学习成本，通用能力沉淀到 `frontend/packages/` 的 `@pet/ui`、`@pet/utils`）。

新潮备选（若追求更强设计感）：SoybeanAdmin、Vben Admin、shadcn/ui + Tailwind —— 不推荐本项采用，团队资产复用优先。

## 5. 基础设施

| 类别 | 选型 | 说明 |
| ---- | ---- | ---- |
| 对象存储 | 腾讯云 COS（或阿里云 OSS） | 宠物图片、详情视频；服务端签发直传凭证，前端直传 |
| CDN | 厂商 CDN | 图片/视频加速，详情页首屏体验关键 |
| 反向代理 | Nginx | TLS 终结、路由、静态托管（H5/管理端） |
| 部署 | Docker Compose（起步）→ K8s（按需） | 后端单服务，PG/Redis 独立实例 |
| CI/CD | GitHub Actions / Jenkins | 小程序发布走 miniprogram-ci |
| 可观测 | go-zero logx + PG 慢查询日志 | 起步阶段轻量方案，后续接 Prometheus |
