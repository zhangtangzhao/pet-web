信息架构

移动端 36 个现存页面收敛为 4 个一级 Tab + 6 组任务；桌面按工作域分组。

移动端一级导航

  • 首页：可购宠物、健康筛选、信任承诺、活动入口。
  • 发现：分类/筛选列表、养宠百科、AI 选宠、晒单广场。
  • 消息：订单、客服、优惠券、系统通知。
  • 我的：账户、订单/售后、宠物档案、营销资产、服务设置。

我的页分组

  • 资产与订单：订单、售后、评价、发票。
  • 宠物服务：宠物档案、预约、保险、配种。
  • 权益与营销：优惠券、积分、积分商城、邀请、任务、会员。
  • 账户与偏好：地址、收藏、消息设置、协议、客服。

桌面后台导航分组

  • 经营：看板、数据大屏、经营报表。
  • 商品与库存：宠物商品、分类品种、供货商、门店。
  • 交易履约：订单、售后、配送方式、预约核销。
  • 增长与客服：营销、活动、会员、评价、人工客服。
  • 平台：财务、审计、敏感词、首页装修、Banner。

全量交互规则

规则按可复用组件抽象，桌面与移动端共用状态语义。

导航与返回

  • 四个一级 Tab 使用原生 TabBar，切换保留滚动位置。
  • 详情类页面入栈，返回不重置列表筛选。
  • 所有登录跳转携带完整 redirect，登录后恢复原任务。
  • 可恢复筛选状态写入 URL。

列表与筛选

  • 筛选变化采用 300ms 防抖请求，取消旧请求。
  • 触底加载显示骨架卡，加载失败显示重试条。
  • 空态提供“清除筛选”和“查看全部”。
  • 切分类/价格/性别保留已选排序。

商品详情

  • 健康档案先于营销内容，异常值显示“待补充”。
  • 有 SKU 必选；未选时购买按钮引导展开 SKU。
  • 收藏乐观更新，失败回滚并提示。
  • 图片支持预览，视频只进入详情后加载。

结算

  • 金额变化区段定位：商品、服务、券、会员、运费、定金。
  • 定金、积分、优惠券互斥关系实时展示禁用原因。
  • 配送方式切换时清空不相关地址输入。
  • 提交按钮双防重；协议未勾选不清空表单。

订单与售后

  • 待支付展示截止时间与可取消操作。
  • 自提已支付单突出核销码并可复制。
  • 可售后才显示申请入口；待审核可撤销。
  • 危险操作必须确认并说明结果。

消息与后台

  • 未读使用小红点，不常驻“已载入”文案。
  • 消息已读乐观更新，失败回滚。
  • 桌面表格保存列宽、筛选与分页。
  • 写操作提供二次确认、加载态、403 提示。

前端交接

方向确认后可分三批进入实现。

P0 · 可直接实现

  • 设计 Token 与基础组件样式。
  • 首页、列表、详情、结算、订单详情。
  • 修复分类参数、登录 redirect、返回语义、TabBar。

P1 · 高价值补齐

  • 我的页分组与营销资产聚合。
  • 消息直达订单、客服与通知中心。
  • 宠物档案和健康提醒入口。

P2 · 桌面重构

  • 后台菜单按工作域折叠。
  • 列表 + 详情抽屉、批量操作、审计反馈。
  • 大屏与报表保留桌面专用密度。

需要业务确认

这些项目不能从代码唯一推导，未确认前不进入默认跳转或首页装修。

跳转范围

  • “跳转相关功能”是 Banner 目标跳转、模块入口聚合，还是修复现有跳转缺陷？
  • 消息中心是否需要按订单号、客服会话、优惠券分别直达？
  • 晒单、任务、砍价、竞拍、预约、保险、配种是否都属于本期 C 端一级能力？

平台与资产

  • 优先交付微信小程序还是 H5？
  • 是否优先重构 C 端，后台桌面进入第二批？
  • 品牌色、Logo、真实宠物照片和运营素材由哪方提供？
  • 支付结果页是否可新增独立路由，还是必须停留在订单详情？

本页是设计方向样机与交互规格，不是最终上线页面。样机中的价格、库存与健康状态均为示意数据。
